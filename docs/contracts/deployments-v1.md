# Pinforth API Contract: Deployment Tracking (v1)

**Status:** READY FOR FRONTEND REVIEW
**Version:** 1.0.0
**Base Path:** `/api/v1`
**Feature branch:** `feat/deployments-api`

---

## 1. Purpose and Scope

Pinforth is adding immutable deployment records to website environments. A deployment identifies a concrete version of a website that reviewers, developers and clients can talk about unambiguously, for example:

- `v1.0`
- `v1.5`
- `release-candidate-2`

This phase exposes the deployment foundation:

- Record a deployment manually for an environment.
- List deployments for an environment with cursor pagination.
- Read one deployment.
- Expose the latest recorded deployment for every environment in the existing project detail response.

Later phases will reference these records when developers submit fixes, QA testers verify fixes on an exact deployment, and clients approve a release. This phase does **not** implement fix submissions, QA verification, issue status changes, release readiness, client approval, CI/CD ingestion, attachments, screenshots, AI, or any frontend UI.

A deployment record is immutable. If a deployment was recorded incorrectly, record a new deployment instead of editing or deleting the original.

### Important definition

`latestDeployment` means **the most recently recorded deployment**, not proof that this version is currently live on the website. Pinforth does not fetch, probe or detect live deployments in this phase.

## 2. Data Model: `Deployment`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key, generated by the API. |
| `environmentId` | UUID | Owning environment. Required. |
| `label` | varchar(100) | Human version label, trimmed. Unique within its environment. |
| `commitSha` | varchar(40), nullable | Optional git commit SHA, 7–40 hexadecimal characters. |
| `url` | varchar(2048), nullable | Optional HTTP/HTTPS URL for this version. |
| `notes` | text, nullable | Optional release notes, maximum 2,000 characters after trimming. |
| `createdById` | UUID, nullable | Creator. References `User`. `SET NULL` if the user row is removed, so the deployment history is preserved. |
| `createdAt` | timestamptz(3) | Database default. Never changes. |

There is intentionally **no** `updatedAt` column.

### Constraints and indexes

- `PRIMARY KEY (id)`.
- `UNIQUE (environmentId, label)` — labels are unique per environment at the database level.
- `INDEX (environmentId, createdAt, id)` — supports newest-first keyset listing.
- `environmentId` references `Environment(id)` with `ON DELETE RESTRICT`, so deployment history cannot be silently destroyed by deleting its environment.
- `createdById` references `User(id)` with `ON DELETE SET NULL`, so a deployment survives creator account removal.

Labels must not be unique globally. Two environments, including two environments in the same project, may record the same label.

### Label case sensitivity

Label uniqueness is **case-sensitive** after trimming. `v1.5` and `V1.5` are different labels and may both exist in one environment. The frontend should not silently lower-case or otherwise rewrite a label, because that would make the read-back recovery described in section 11 ambiguous.

## 3. Global Conventions

### Response envelope

Success (2xx):

```json
{
  "success": true,
  "data": { ... }
}
```

Failure (4xx, 5xx):

```json
{
  "success": false,
  "code": "ERROR_CODE",
  "message": "Human-readable explanation",
  "details": [ ... ]
}
```

`details` is present only for validation errors, matching the existing Pinforth API.

### Deployment representation

Every endpoint that returns a deployment returns the same shape:

```json
{
  "id": "8d7b7f6b-4f0c-4c1b-9d6f-9a0f2a6c1e11",
  "environmentId": "4c424a52-c380-4cf8-a968-380d3211516e",
  "label": "v1.5",
  "commitSha": "a1b2c3d",
  "url": "https://staging.example.com",
  "notes": "Checkout and responsive navigation fixes.",
  "createdBy": {
    "id": "b1f6d6d0-7a1c-4f6d-9f2c-1c2f7a8b9c01",
    "name": "Priya"
  },
  "createdAt": "2026-11-26T10:15:30.000Z"
}
```

- Optional fields are `null` when absent, never omitted from the object.
- `createdBy` is `null` if the creator's user row has been removed.
- `createdBy.email` is never returned.
- No internal fields, password material, tokens, or environment credentials are exposed.

## 4. Authorization

All deployment endpoints use the existing organization → project → environment hierarchy:

```text
/api/v1/organizations/:orgId/projects/:projectSlug/environments/:environmentId/deployments
```

Every route requires authentication. The organization membership, project and environment are resolved with the existing Pinforth middleware before the deployment handler runs.

| Action | Who | Additional rule |
| --- | --- | --- |
| Create deployment | `OWNER`, `ADMIN`, `MEMBER` | Verified email required. |
| List deployments | Any organization member | — |
| Read one deployment | Any organization member | — |
| Update / delete deployment | Nobody | No endpoint exists. |

- The creator is always `req.auth.userId` from the authenticated session. The API never accepts `createdById`, `createdBy`, `id`, `createdAt`, or any other server-owned field in the request body.
- A caller who is not a member of `:orgId` receives the same `404 NOT_FOUND` response as a missing organization, so organization IDs cannot be probed.
- A project or environment from another tenant is also `404 NOT_FOUND`, not `403`.
- Authorization and tenant resolution run before request-body validation. A non-member therefore learns nothing from an invalid body.

---

## 5. Tenant Isolation and Ownership

The server enforces all of the following on every request:

1. `:orgId` matches the caller's membership.
2. `:projectSlug` is looked up only inside that organization.
3. `:environmentId` is looked up only inside that project.
4. A deployment is queried only with the resolved `environmentId` in the `WHERE` clause.

A deployment ID that exists in another environment, project or organization is indistinguishable from a deployment that does not exist. Both return `404 NOT_FOUND`.

Malformed organization, project, environment or deployment identifiers also return `404 NOT_FOUND`, matching the existing project and environment endpoints. They are never treated as a successful empty result.

## 6. Create Deployment

```http
POST /api/v1/organizations/:orgId/projects/:projectSlug/environments/:environmentId/deployments
```

### Request body

```json
{
  "label": "v1.5",
  "commitSha": "a1b2c3d",
  "url": "https://staging.example.com",
  "notes": "Checkout and responsive navigation fixes."
}
```

Only `label` is required.

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| `label` | string | Yes | Trimmed. 1–100 characters. Cannot be empty or whitespace-only. |
| `commitSha` | string \| null | No | Trimmed. 7–40 hexadecimal characters (`0-9`, `a-f`, `A-F`). `""`, whitespace-only, `null`, or omitted becomes `null`. |
| `url` | string \| null | No | Trimmed. HTTP or HTTPS only. Maximum 2,048 characters. Embedded credentials are rejected. `""`, whitespace-only, `null`, or omitted becomes `null`. |
| `notes` | string \| null | No | Trimmed. Maximum 2,000 characters. `""`, whitespace-only, `null`, or omitted becomes `null`. |

Unknown fields are rejected with `400 VALIDATION_ERROR` (strict validation). This includes `id`, `environmentId`, `createdById`, `createdBy`, `createdAt` and any deployment-update fields.

### Response `201 Created`

```json
{
  "success": true,
  "data": {
    "deployment": {
      "id": "8d7b7f6b-4f0c-4c1b-9d6f-9a0f2a6c1e11",
      "environmentId": "4c424a52-c380-4cf8-a968-380d3211516e",
      "label": "v1.5",
      "commitSha": "a1b2c3d",
      "url": "https://staging.example.com",
      "notes": "Checkout and responsive navigation fixes.",
      "createdBy": {
        "id": "b1f6d6d0-7a1c-4f6d-9f2c-1c2f7a8b9c01",
        "name": "Priya"
      },
      "createdAt": "2026-11-26T10:15:30.000Z"
    }
  }
}
```

### Duplicate label response `409 Conflict`

```json
{
  "success": false,
  "code": "DEPLOYMENT_LABEL_TAKEN",
  "message": "A deployment with this label already exists in this environment"
}
```

Uniqueness is enforced by the database unique constraint, not by a check-then-insert sequence. If two requests with the same environment and label arrive concurrently, exactly one succeeds with `201` and the other returns `409 DEPLOYMENT_LABEL_TAKEN`. A duplicate attempt never creates a second row.

### Create error responses

| Status | Code | When |
| --- | --- | --- |
| `400` | `VALIDATION_ERROR` | Missing/empty/invalid label, invalid commit SHA, unsafe or invalid URL, over-length notes, unknown field. |
| `401` | `UNAUTHORIZED` | No valid access session. |
| `403` | `EMAIL_NOT_VERIFIED` | Member has not verified their email address. |
| `404` | `NOT_FOUND` | Organization, project or environment is missing or outside the caller's tenant. |
| `409` | `DEPLOYMENT_LABEL_TAKEN` | Label already exists in this environment. |
| `500` | `INTERNAL_ERROR` | Unexpected failure. Internal details are not returned. |

## 7. List Deployments

```http
GET /api/v1/organizations/:orgId/projects/:projectSlug/environments/:environmentId/deployments?limit=20&cursor=<opaque>
```

### Query parameters

| Name | Type | Default | Rules |
| --- | --- | --- | --- |
| `limit` | integer | `20` | 1–100 inclusive. `0`, `101`, decimals and non-numeric values fail validation. |
| `cursor` | string | absent | Opaque value from a previous `nextCursor`. Do not construct or parse it on the client. |

Unknown query parameters are rejected with `400 VALIDATION_ERROR`, consistent with the existing issue and timeline list endpoints.

### Response `200 OK`

```json
{
  "success": true,
  "data": {
    "deployments": [
      {
        "id": "8d7b7f6b-4f0c-4c1b-9d6f-9a0f2a6c1e11",
        "environmentId": "4c424a52-c380-4cf8-a968-380d3211516e",
        "label": "v1.5",
        "commitSha": "a1b2c3d",
        "url": "https://staging.example.com",
        "notes": "Checkout and responsive navigation fixes.",
        "createdBy": { "id": "b1f6d6d0-7a1c-4f6d-9f2c-1c2f7a8b9c01", "name": "Priya" },
        "createdAt": "2026-11-26T10:15:30.000Z"
      }
    ],
    "nextCursor": null
  }
}
```

Empty environment:

```json
{
  "success": true,
  "data": {
    "deployments": [],
    "nextCursor": null
  }
}
```

- `deployments` is always an array.
- `nextCursor` is `null` when there are no more pages. There is intentionally no `hasMore` field; `nextCursor !== null` is the signal.
- Pass `nextCursor` back as `cursor` to fetch the next page.

### Ordering and cursor semantics

Results are ordered by:

```text
createdAt DESC, then id DESC
```

`createdAt` is stored with millisecond precision. `id` makes the order total and deterministic when multiple deployments share the same timestamp, so pages never overlap or skip records.

The cursor is base64url of:

```text
<createdAt ISO-8601>|<deployment UUID>
```

It is opaque. Clients must treat it as a string and must not build it themselves. The API rejects malformed cursors with `400 BAD_REQUEST` and message `Invalid cursor`.

The query is keyset-based, not offset-based. Inserting a newer deployment between page requests does not duplicate or skip older deployments already reached by the cursor.

### List error responses

| Status | Code | When |
| --- | --- | --- |
| `400` | `VALIDATION_ERROR` | Invalid `limit`, unknown query parameter, cursor longer than the accepted maximum. |
| `400` | `BAD_REQUEST` | Malformed cursor (`Invalid cursor`). |
| `401` | `UNAUTHORIZED` | No valid access session. |
| `404` | `NOT_FOUND` | Organization, project or environment missing or outside the caller's tenant. |
| `500` | `INTERNAL_ERROR` | Unexpected failure. |

## 9. Immutability

There is deliberately no update or delete endpoint:

| Method | Result |
| --- | --- |
| `PATCH /.../deployments` or `/.../deployments/:deploymentId` | `404 ROUTE_NOT_FOUND` |
| `PUT /.../deployments/:deploymentId` | `404 ROUTE_NOT_FOUND` |
| `DELETE /.../deployments/:deploymentId` | `404 ROUTE_NOT_FOUND` |

No service method modifies or deletes an existing deployment. An incorrect record is corrected by creating a new deployment with a new label. Older records remain part of the deployment history.

This is intentional: later verification and client approval will belong to a specific deployment, and editing that deployment after approval would undermine the record.

## 10. Latest Deployment in Project Detail

The existing project detail endpoint is extended additively:

```http
GET /api/v1/organizations/:orgId/projects/:projectSlug
```

Each environment now includes a `latestDeployment` field:

```json
{
  "success": true,
  "data": {
    "project": {
      "id": "7c126d41-e945-4290-8451-b8417934c9f1",
      "name": "Client Brand Website",
      "slug": "client-brand-website",
      "description": "Marketing site",
      "createdAt": "2026-11-01T09:00:00.000Z",
      "updatedAt": "2026-11-20T12:00:00.000Z",
      "environments": [
        {
          "id": "4c424a52-c380-4cf8-a968-380d3211516e",
          "name": "Staging",
          "slug": "staging",
          "url": "https://staging.example.com",
          "createdAt": "2026-11-02T09:00:00.000Z",
          "updatedAt": "2026-11-02T09:00:00.000Z",
          "latestDeployment": {
            "id": "8d7b7f6b-4f0c-4c1b-9d6f-9a0f2a6c1e11",
            "label": "v1.5",
            "createdAt": "2026-11-26T10:15:30.000Z"
          }
        }
      ]
    }
  }
}
```

When an environment has no deployments:

```json
{
  "latestDeployment": null
}
```

Rules:

- `latestDeployment` is selected with the same deterministic ordering as the list: `createdAt DESC, id DESC`.
- Only `id`, `label` and `createdAt` are included.
- All existing project and environment fields are preserved.
- The value is the latest **recorded** deployment, not a live-deployment check.
- The project detail endpoint remains readable by any organization member.

## 11. Duplicate Submission and Retry Behavior

Deployment creation has no separate idempotency-key system in this phase. The unique `(environmentId, label)` constraint is the recovery anchor.

If the frontend does not receive a definite response (timeout, network failure, transport error), it may:

1. `GET` the environment's deployment list, paginating with `nextCursor` if needed.
2. Look for the submitted `label`.
3. Compare the stored deployment details (`commitSha`, `url`, `notes`) with what was submitted.

Decision rules:

- A matching label with matching submitted fields can be presented as the successful earlier submission.
- A matching label with different fields is **not** proof that the earlier request succeeded as intended. Show a conflict and ask the user to choose a different label or review the existing record.
- No match means the request can be retried with the same label.
- Never create a second deployment merely because the first response was uncertain.

A direct repeated creation with an existing environment + label returns `409 DEPLOYMENT_LABEL_TAKEN`; it does not return the existing record and does not create a duplicate.

The frontend owns the recovery interface. The backend guarantees the uniqueness and the read APIs needed to implement it.

## 12. Validation Rules

| Input | Rule | Failure |
| --- | --- | --- |
| `label` | String, trimmed, 1–100 characters | `400 VALIDATION_ERROR` |
| `commitSha` | Optional/nullable; after trim, 7–40 hexadecimal characters; `""`/whitespace becomes `null` | `400 VALIDATION_ERROR` |
| `url` | Optional/nullable; after trim, valid absolute `http://` or `https://` URL, max 2,048 characters, no username/password; `""`/whitespace becomes `null` | `400 VALIDATION_ERROR` |
| `notes` | Optional/nullable; after trim, max 2,000 characters; `""`/whitespace becomes `null` | `400 VALIDATION_ERROR` |
| Unknown body fields | Rejected | `400 VALIDATION_ERROR` |
| `:orgId` | Must be a UUID the caller belongs to | Missing/invalid/foreign → `404 NOT_FOUND` |
| `:projectSlug` | Existing slug inside that organization | Missing/invalid/foreign → `404 NOT_FOUND` |
| `:environmentId` | UUID inside that project | Missing/invalid/foreign → `404 NOT_FOUND` |
| `:deploymentId` | UUID inside that environment | Missing/invalid/foreign → `404 NOT_FOUND` |
| `limit` | Integer 1–100, default 20 | `400 VALIDATION_ERROR` |
| `cursor` | Opaque value previously returned as `nextCursor` | Malformed → `400 BAD_REQUEST` (`Invalid cursor`) |

Optional fields do not use `undefined` in responses. The API stores absent, blank, and explicit `null` values as database `NULL` and serializes them as JSON `null`.

### URL safety

Only `http` and `https` are accepted. `javascript:`, `data:`, `file:`, `ftp:` and any other scheme are rejected. Embedded credentials such as `https://user:password@host` are rejected so staging passwords are not stored. The backend never fetches a deployment URL to validate it.

Request 1:

Response:

```json
{
  "success": true,
  "data": {

    "nextCursor": "MjAyNi0xMS0yMlQwOTowMDowMC4wMDBafGRlcC1iLi4u"

```

Returns the next older deployments with no duplicates. The abbreviated IDs above are illustrative; real IDs are UUIDs.

## 14. Edge Cases

- **No deployments:** `200` with `deployments: []`, `nextCursor: null`, and `latestDeployment: null` on the project detail.
- **Same label in another environment:** allowed. Labels are scoped to the environment.
- **Same label in another organization/project:** allowed for the same reason.
- **Same label with different casing in one environment:** allowed; uniqueness is case-sensitive.
- **Concurrent identical creates:** exactly one `201`, one `409 DEPLOYMENT_LABEL_TAKEN`, one stored row.
- **Repeated create after uncertain network result:** expect `409`; use the list read-back strategy in section 11.
- **Creator account removed:** deployment remains, `createdBy` becomes `null`.
- **Environment deletion:** blocked while deployments exist by the `ON DELETE RESTRICT` foreign key. There is no environment delete endpoint in this phase.
- **Deployment from another tenant:** `404 NOT_FOUND`, never `403` and never partial data.
- **Equal `createdAt` values:** ordering falls back to `id DESC`; pagination remains stable.
- **Fields left blank:** optional fields become `null`; `label` cannot be blank.
- **URL not fetched:** validation is syntactic only. A URL that returns an error is still a valid record.
- **No update or delete:** mutation methods return `404 ROUTE_NOT_FOUND` and cannot modify stored data.
