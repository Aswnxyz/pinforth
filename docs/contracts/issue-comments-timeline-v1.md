# Pinforth API Contract: Issue Comments & Activity Timeline (v1)

**Status:** READY FOR FRONTEND REVIEW
**Version:** 1.0.0
**Base Path:** `/api/v1`
**Feature branch:** `feat/issue-comments-activity-timeline`

---

## 1. Purpose and Scope

Every issue now has a conversation and an auditable history:

- **Comments** let organization members discuss an issue in one place instead of WhatsApp, email, or a call.
- **Activity** records the meaningful changes made to an issue (status, priority, type, assignee, title, description), with the actor and the affected values.
- **Timeline** returns comments and activity as one chronological, paginated stream.

In scope: member-authored comments, comment editing and soft deletion, activity capture on every existing issue mutation path, the timeline endpoint, and `commentsCount` on issue lists.

Out of scope: guest comment creation, guest timeline access, notifications, edits history for comments (only the latest body is retained), attachments on comments, and frontend work. The data model leaves a documented extension point for guest authorship (section 18).

---

## 2. Data Model: `IssueComment`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key, generated by the API. |
| `issueId` | UUID | Owning issue. Cascades when the issue is deleted. |
| `authorId` | UUID, nullable | Author. References `User`. `SET NULL` if the user row is removed. Nullable so guest authorship can be added later. Empty in this version. |
| `body` | text | Original comment text. Max 10,000 characters, enforced by validation before insert. Never silently truncated. |
| `visibility` | enum | `PUBLIC` or `INTERNAL`. Default `PUBLIC`. |
| `createdAt` | timestamptz(3) | Database default. Never changes. |
| `editedAt` | timestamptz(3), nullable | `null` until the author edits the body. |
| `deletedAt` | timestamptz(3), nullable | `null` until soft deletion. |

Indexes: `(issueId, createdAt)` for timeline reads, `(authorId)` for author lookups. There is intentionally no `visibility` index in this version: member-facing timeline queries do not filter on visibility. A `(issueId, visibility, createdAt)` index should be added with the guest timeline.

Deletion is always soft. No normal endpoint physically deletes a comment row.

## 3. Data Model: `IssueActivity`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key. |
| `issueId` | UUID | Owning issue. Cascades when the issue is deleted. |
| `actorId` | UUID, nullable | Authenticated user who performed the change. `SET NULL` if the user row is removed. Null for system/guest-created issues. |
| `type` | enum | See below. |
| `oldValue` | jsonb, nullable | Previous value, shape depends on `type`. |
| `newValue` | jsonb, nullable | New value, shape depends on `type`. |
| `createdAt` | timestamptz(3) | Database default. |

Indexes: `(issueId, createdAt)` for timeline reads.

### Activity types and value shapes

| `activityType` | `oldValue` | `newValue` | Timeline copy |
| --- | --- | --- | --- |
| `ISSUE_CREATED` | `null` | `null` | "Priya created this issue." |
| `STATUS_CHANGED` | enum string, e.g. `"NEW"` | enum string, e.g. `"IN_PROGRESS"` | "changed status from NEW to IN_PROGRESS" |
| `PRIORITY_CHANGED` | enum string | enum string | "changed priority from MEDIUM to HIGH" |
| `TYPE_CHANGED` | enum string | enum string | "changed type from BUG to DESIGN" |
| `ASSIGNEE_CHANGED` | `{ "id": uuid, "name": string \| null }` or `null` | `{ "id": uuid, "name": string \| null }` or `null` | "assigned this issue to Sachin" / "unassigned this issue" |
| `TITLE_CHANGED` | previous title string | new title string | "changed the title" |
| `DESCRIPTION_CHANGED` | `null` | `null` | "updated the description" |

Description values are not stored because a description can be 10,000 characters; the activity records that it changed, not its full history. Assignee name is snapshotted at the time of the change so history stays readable after a rename or removal.

### Activity integrity

Every tracked issue change and its activity row are written in one database transaction:

1. Read the current issue state inside the transaction.
2. Compare each submitted tracked field with the stored value.
3. Update the issue.
4. Insert one activity row per field that actually changed.
5. Commit.

If activity insertion fails, the issue update rolls back. Issue creation (dashboard and widget) also inserts `ISSUE_CREATED` in the same transaction as the issue row and issue-number increment.

An update that submits a value equal to the stored value creates no activity row. Fields outside the seven tracked types (environment, timestamps, source, page URL, context) never create activity.

### Actor attribution

The actor is always the authenticated user from the session. The API never accepts an actor, author, reporter, or member ID for attribution from the request body.

## 4. Visibility Rules

| Visibility | Organization members | Guests (future) |
| --- | --- | --- |
| `PUBLIC` | Visible | Eligible to be visible when guest timeline support is added. |
| `INTERNAL` | Visible | Never visible. |

Visibility is enforced on the server:

- The member timeline returns both visibilities.
- No guest-facing endpoint returns comments in this version. When a guest timeline is added it must filter `visibility = PUBLIC AND deletedAt IS NULL`.
- Internal comment text is never included in error messages, logs, or any issue serializer. Issue list/detail responses carry only `commentsCount`, never comment bodies.

Visibility is immutable through the edit endpoint. Turning an internal note into a public comment is not supported.

---

## 5. Authorization Rules

All endpoints below run after the existing `requireAuth`, `requireOrgRole()` (organization membership), and `requireProject` middleware. A user who is not a member of `:orgId` receives `404 NOT_FOUND`, the same response as a missing organization, so tenant IDs cannot be probed.

| Action | Rule |
| --- | --- |
| Read timeline | Any member of the organization. |
| Create comment | Any member of the organization with a verified email. |
| Edit comment | The original author only. Other members receive `403 FORBIDDEN`. |
| Delete comment | The original author, or an organization `OWNER` / `ADMIN`. Other members receive `403 FORBIDDEN`. |
| Edit/delete a deleted comment | Edit: `409 CONFLICT`. Delete: idempotent success (see §12). |

Comments are addressable only through their issue, and the issue is addressable only through the organization + project in the URL. A comment ID from another organization is therefore unreachable and returns `404 NOT_FOUND`.

---

## 6. Tenant Isolation

- `:orgId` is validated against the caller's membership.
- `:projectSlug` is looked up only inside `:orgId`.
- `:number` is looked up only inside that project (`@@unique([projectId, number])`).
- `:commentId` is looked up with `issueId` constrained to that project's issue.
- Missing and cross-tenant resources both return `404 NOT_FOUND`, without revealing whether the resource exists.

## 7. Timeline Endpoint

```
GET /api/v1/organizations/:orgId/projects/:projectSlug/issues/:number/timeline
```

Query parameters:

| Name | Type | Default | Rules |
| --- | --- | --- | --- |
| `limit` | integer | `20` | 1 to 100. Values outside the range fail validation. |
| `cursor` | string | absent | Opaque cursor returned as `pagination.nextCursor`. Max 200 characters. |

The endpoint is read-only and requires a member session.

### Response `200 OK`

```json
{
  "success": true,
  "data": {
    "timeline": [
      {
        "id": "0a1f0f5e-8a2e-4a18-b80e-6f6f4f6a1f10",
        "type": "ACTIVITY",
        "activityType": "ISSUE_CREATED",
        "actor": { "id": "b1f6d6d0-7a1c-4f6d-9f2c-1c2f7a8b9c01", "name": "Priya" },
        "oldValue": null,
        "newValue": null,
        "createdAt": "2026-11-16T09:15:00.000Z"
      },
      {
        "id": "5c5a1d6e-2b3f-4a44-9d61-2b0c7f8e9a12",
        "type": "COMMENT",
        "author": { "id": "b1f6d6d0-7a1c-4f6d-9f2c-1c2f7a8b9c01", "name": "Priya" },
        "body": "The login button is not working on Safari.",
        "visibility": "PUBLIC",
        "createdAt": "2026-11-16T09:20:00.000Z",
        "editedAt": null,
        "deletedAt": null
      },
      {
        "id": "9e8d7c6b-5a49-4382-8170-6f5e4d3c2b1a",
        "type": "ACTIVITY",
        "activityType": "STATUS_CHANGED",
        "actor": { "id": "c2e7e7e1-8b2d-4a5e-8a3d-2d3a8b9c0d02", "name": "Sachin" },
        "oldValue": "NEW",
        "newValue": "IN_PROGRESS",
        "createdAt": "2026-11-16T10:02:00.000Z"
      }
    ],
    "pagination": {
      "limit": 20,
      "nextCursor": null,
      "hasMore": false
    }
  }
}
```

- `timeline` is ordered **oldest first**.
- Entries are a discriminated union on `type`: `"COMMENT"` or `"ACTIVITY"`.
- A deleted comment is returned as a tombstone: `body` is `null`, `deletedAt` is set, and `author`, `visibility`, and `createdAt` are preserved for continuity.
- Actor/author objects contain `id` and `name` only; email is not included in the timeline.
- `nextCursor` is `null` when `hasMore` is `false`. Pass it back as `cursor` to fetch the next page.

### Ordering and cursor semantics

The server orders the merged stream by `(createdAt ASC, id ASC)`. `id` is the deterministic tie-breaker for records created in the same millisecond. The cursor encodes that pair as base64url of `<createdAt ISO-8601>|<id>` and is opaque to clients.

The query is a keyset query: each page fetches records after the cursor pair from both tables, merges them, and returns the first `limit` entries. Because the ordering key is immutable and unique, entries inserted between page requests do not cause duplicates or skips of older entries. Row order from PostgreSQL is never used.

Invalid cursors (bad base64, bad timestamp, non-UUID id) return `400 BAD_REQUEST` with code `BAD_REQUEST` and message `Invalid cursor`.

## 8. Create Comment Endpoint

```
POST /api/v1/organizations/:orgId/projects/:projectSlug/issues/:number/comments
```

Requires a member session and a verified email (same rule as issue creation).

Request:

```json
{
  "body": "The login button is not working on Safari.",
  "visibility": "PUBLIC"
}
```

| Field | Required | Rules |
| --- | --- | --- |
| `body` | Yes | Trimmed. Non-empty. Max 10,000 characters. |
| `visibility` | No | `PUBLIC` (default) or `INTERNAL`. |

The author is the authenticated user. Sending `authorId`, `issueId`, `id`, `createdAt`, `deletedAt`, or any other unknown field is rejected by strict validation with `400 VALIDATION_ERROR`.

Response `201 Created`:

```json
{
  "success": true,
  "data": {
    "comment": {
      "id": "5c5a1d6e-2b3f-4a44-9d61-2b0c7f8e9a12",
      "issueId": "0f2b8c1d-4e5f-4a6b-8c9d-0e1f2a3b4c5d",
      "author": { "id": "b1f6d6d0-7a1c-4f6d-9f2c-1c2f7a8b9c01", "name": "Priya" },
      "body": "The login button is not working on Safari.",
      "visibility": "PUBLIC",
      "createdAt": "2026-11-16T09:20:00.000Z",
      "editedAt": null,
      "deletedAt": null
    }
  }
}
```

Creating a comment does **not** create an activity row; the comment is already a timeline entry.

## 9. Edit Comment Endpoint

```
PATCH /api/v1/organizations/:orgId/projects/:projectSlug/issues/:number/comments/:commentId
```

Request:

```json
{ "body": "The login button is unresponsive on Safari 18." }
```

Rules:

- Only the original author may edit; anyone else gets `403 FORBIDDEN`.
- `body` is required, trimmed, non-empty, max 10,000 characters.
- Only `body` is accepted. `visibility`, `issueId`, `authorId`, `createdAt`, and `deletedAt` are rejected by strict validation.
- `editedAt` is set to the current time. `createdAt` never changes.
- A soft-deleted comment returns `409 CONFLICT` with code `CONFLICT`.

Response `200 OK` returns `{ "success": true, "data": { "comment": { ... } } }` with the updated comment, including `editedAt`.

---

## 10. Delete Comment Endpoint

```
DELETE /api/v1/organizations/:orgId/projects/:projectSlug/issues/:number/comments/:commentId
```

Allowed for the original author or an organization `OWNER` / `ADMIN`.

Behavior:

- Sets `deletedAt` to the current time. The row and original body remain in the database.
- The response never includes the body.
- Repeated deletion is safe and idempotent: `deletedAt` is not moved, and the endpoint still returns `200 OK`.
- Deleted comments cannot be edited (`409 CONFLICT`).

Response `200 OK`:

```json
{
  "success": true,
  "data": { "deleted": true, "commentId": "5c5a1d6e-2b3f-4a44-9d61-2b0c7f8e9a12" }
}
```

---

## 11. Soft-Deletion Behavior

- Timeline: deleted comments appear as tombstones with `body: null` and `deletedAt` set.
- Issue list/detail: deleted comments are excluded from `commentsCount`.
- No endpoint physically deletes a comment.
- The body remains stored for audit/legal retention and is never serialized after deletion. It must not appear in logs or errors.

---

## 12. `commentsCount` on Issue Lists

Every issue in `GET /api/v1/organizations/:orgId/projects/:projectSlug/issues` now includes:

```json
{ "commentsCount": 3 }
```

- Counts non-deleted comments only.
- Includes both `PUBLIC` and `INTERNAL` comments for member-facing lists.
- Computed with a single filtered relation count per issue list query — no N+1 queries and no comment bodies loaded.
- Also present in issue detail and issue create/update responses because they share the summary serializer.
- The widget issue serializer is unchanged and does not expose comment data.

## 13. Validation Rules

| Input | Rule | Failure |
| --- | --- | --- |
| Comment `body` | String, trimmed, min 1, max 10,000 characters | `400 VALIDATION_ERROR` |
| Comment `visibility` | `PUBLIC` or `INTERNAL` | `400 VALIDATION_ERROR` |
| Edit body | Same as create, `body` only | `400 VALIDATION_ERROR` |
| Timeline `limit` | Integer 1–100, default 20 | `400 VALIDATION_ERROR` |
| Timeline `cursor` | Valid opaque cursor | `400 BAD_REQUEST` (`Invalid cursor`) |
| Issue `:number` | Positive integer, exists in project | `404 NOT_FOUND` |
| Comment `:commentId` | UUID, exists on that issue | `404 NOT_FOUND` |
| Unknown request fields | Strict schemas reject them | `400 VALIDATION_ERROR` |

Bodies are validated before insert; the API never truncates a comment to fit.

---

## 14. Error Responses

Standard envelope:

```json
{
  "success": false,
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "details": [{ "path": "body", "message": "Comment is required" }]
}
```

| Status | Code | When |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Zod validation failure (empty body, too long, bad visibility, bad limit, unknown field). |
| 400 | `BAD_REQUEST` | Malformed timeline cursor. |
| 401 | `UNAUTHORIZED` | No valid session. |
| 403 | `FORBIDDEN` | Editing another member's comment, or non-author/non-admin attempting deletion. |
| 403 | `EMAIL_NOT_VERIFIED` | Unverified member creating a comment. |
| 404 | `NOT_FOUND` | Issue or comment does not exist in the caller's organization/project (also used for cross-tenant access). |
| 409 | `CONFLICT` | Editing a soft-deleted comment. |
| 500 | `INTERNAL_ERROR` | Unexpected failure; no internal details or comment text are returned. |

## 16. Known Limitations and Decisions

- Comment edit history is not retained; only the latest body and `editedAt` are exposed. Deleted bodies remain in the database but are never returned.
- `INTERNAL` comments are member-only in this version. Guest timeline support must add a `visibility = PUBLIC` filter and a guest-specific serializer.
- Activity for `DESCRIPTION_CHANGED` intentionally stores no values (size). Title changes store old/new titles.
- Environment changes, source changes, and page-context changes are not tracked activity types in v1.
- Physically deleting an issue still cascade-deletes its comments and activity, matching the existing hard-delete issue behavior.
- The widget/guest issue API is unchanged; it exposes no comments, counts, or timeline.

## 17. Guest-Authorship Extension Point

Guest authorship is intentionally not implemented. The model supports it without a redesign:

- `IssueComment.authorId` is nullable.
- `IssueComment.visibility` already distinguishes `PUBLIC` from `INTERNAL`.
- A future migration can add a nullable `guestLinkId` (and/or `guestSessionId`) relation to `GuestAccessLink`; exactly one of `authorId` / `guestLinkId` identifies the author.
- Guest-facing reads must filter `deletedAt IS NULL AND visibility = 'PUBLIC'`, and guest-facing writes must force `visibility = 'PUBLIC'`.
- The timeline response already models `author` as nullable-safe; a guest author serializer can add a `guest` shape alongside or instead of the member author.

No guest comment permissions, guest activity access, or guest comment creation are exposed by this version.
